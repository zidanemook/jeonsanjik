# 자작문제 모의고사 — 계획서 (2026-09-20, 구현 보류)

사용자 요청: "자체제작문제들로만 모의고사를 만드는 기능. 실제 한능 기출처럼. 범위별로 50문항을
선택해서 모의고사를 만드는거지. 모의고사 시작 누르면 생성되고 그담부턴 시작 버튼이 사라져.
문제를 다 풀면 시작 버튼이 다시 나옴. 다 풀면 기록을 남김, 파이어베이스에. 모의고사 결과도 따로
페이지에서 보여주는거지. 점수, 시험치는데 걸린 시간, 어느 파트가 취약한지. 등등. 순서대로 다
풀어야 하는건 당연하고, 복습도 필요없고. 그냥 모의고사인거지."

**상태: 계획만. 구현 보류.** 사용자가 2026-09-20에 "일단 계획서만 남기고 일단 보류하자"로 정함.

## 1. 확인된 사실 (실측)

| 항목 | 값 | 근거 |
|---|---|---|
| 한능검 1회분 문항 수 | **50문항** | `drill-app.test.cjs` "한능검 79회는 50문항" |
| 자작 한국사 문제 | **1215개** | `CORE_REVIEW_PACK` 중 `subject==='한국사'` |
| 자작 풀에 섞인 기출 | **0개** | `hanneung-*` 0 · `gichul-*` 0 |
| 복습 카탈로그 문항 | 1145개 | `STUDY_REVIEW_CATALOG.questions` |

**자작문제 판별식은 앱에 이미 있다.** `roundMatch`의 `core` 분기가 그대로 쓸 수 있는 정의다:

```js
!Hanneung.get(c.id) && !Gichul.get(c.id)   // 기출이 아니면 자작
```

|---|---:|---|---|---:|---|

여러 강을 묶는 범위(주제·요약자료·전체)를 함께 허용하면 이 문제는 대부분 사라진다.

## 2. 이 기능의 본체는 "즉시 채점을 끄는 것"

지금 앱은 **문제마다 풀면 즉시 채점하고 해설을 보여주는** 흐름이다(`data.quizFeedback`).
모의고사는 그 반대다 — **끝까지 풀고 마지막에 한 번에 채점**한다. 이게 가장 큰 변경이고,
기출 회차(`PAPER ORDER`)조차 하지 않은 일이다. 기출 회차는 원문 순서대로 내되 채점은 평소와 같다.

따라서 모의고사는 기출 회차 모드의 확장이 아니라 **네 번째 출제 모드**다.

| 모드 | 순서 | 채점 | 복습 일정 | 기록 |
|---|---|---|---|---|
| 평소 | 복습 대기열 | 즉시 | 갱신 | events |
| 드릴(전부 풀기) | 카탈로그 순 | 즉시 | 갱신 | events |
| 기출 회차 | 원문 순 | 즉시 | 갱신 | events |
| **모의고사** | **고정(생성 시 확정)** | **끝나고 일괄** | **건드리지 않음** | **별도** |

## 3. 출제 규칙

1. **풀**: 고른 범위 안 `isPlayable` 카드 중 기출 제외(위 판별식).
2. **문항 수**: `min(50, 범위 문항 수)`.
3. **뽑는 방법**: 무작위로 뽑되 **개념(`ReviewPolicy.concept`)이 한쪽에 몰리지 않게** 분산한다.
   같은 개념에서 여러 문항이 나오면 시험이 아니라 드릴이 된다.
4. **변형 고정**: 자작문제는 `PRACTICE_BANK` 변형이 여러 개일 수 있다. 생성 시점에 어떤 변형을
   낼지 확정해 저장한다. 그래야 새로고침해도 같은 시험지가 나온다.
5. **순서 고정**: 생성 시 확정. 중간에 바뀌지 않는다.
6. **복습 무관**: `due`·`retryAt`·형제 간격 무엇도 보지 않고 무엇도 갱신하지 않는다.

## 4. 진행 중 상태 — 새로고침·기기 이동에서 살아남아야 한다

"시작 버튼이 사라진다"는 건 **진행 중 시험이 저장돼 있다**는 뜻이다. 기출 회차의 `paperCursor`는
세션 한정 변수라 그대로 못 쓴다(새로고침하면 사라진다).

```js
data.mockExam = {
  id, scope: {subject, topic, round},
  items: [{cardId, exerciseId}],   // 시험지 — 생성 시 확정
  answers: [{index, choice, at}],  // 푼 것만 쌓임
  startedAt, finishedAt
}
```

- `validateBackup`은 모르는 최상위 키를 막지 않으므로 추가 자체는 가능하다. 다만 **검증을 추가해야**
  손상된 백업이 들어오지 않는다(기존 `quizFeedback` 검증과 같은 방식).
- `leanState`는 `cards`만 손대므로 영향 없다.
- 버튼 상태: `data.mockExam && !finishedAt` 이면 시작 버튼 숨김, 아니면 표시.

## 5. Firestore 기록

### ⚠ 기존 events 컬렉션에 끼워 넣으면 규칙에 막힌다

`firestore.rules:99` 가 `mode in ['quiz','legacy']`로 **화이트리스트**다. `mode:'mock'`은 거부된다.

### 권장: 별도 컬렉션 하나

```
users/{uid}/mockExams/{id}
  { id, scope, startedAt, finishedAt, elapsedMs,
    total, correct,
    items: [{cardId, exerciseId, choice, result}] }
```

- 한 번 치를 때 **문서 1개**. events처럼 문항마다 문서를 만들지 않는다(50개 문서 배치는 낭비).
- `firestore.rules`에 `match /users/{uid}/mockExams/{id}` 추가. events 규칙과 같은 모양으로
  `hasOnly`/`hasAll`/타입 검증을 쓰고, `allow update: if request.resource.data == resource.data`,
  `allow delete: if false`.
- 동기화는 `sync.js`의 events 푸시 옆에 같은 패턴으로 붙인다.

## 6. ⚠ 기존 통계를 오염시키지 않을 것 — 실제 위험 지점

모의고사 답안을 `data.history`에 평소처럼 넣으면 아래가 전부 틀어진다. **각각 제외 처리가 필요하다.**

| 지점 | 파일 | 현재 필터 | 위험 |
|---|---|---|---|
| `firstPass` (첫 시도 N/M) | `app.js:96` | `mode==='quiz'` | 안전 ✓ |
| `solvedOn` (오늘 푼 문제) | `app.js:289` | **mode 필터 없음** | 오염 ✗ |
| `ReviewPolicy.separate` (형제 10분 간격) | `review-policy.js:3246` | 전체 history | 시험 직후 평소 문제가 막힘 ✗ |
| `ReviewPolicy.classify/metrics` (약점 분석) | `review-policy.js` | 전체 history | 시험 답안이 섞임 ✗ |
| `ReviewLearning.assess` (복습 일정) | `learning.js` | — | **아예 호출하지 않는다** |
| `StudyCredit` | `study-credit.js` | 확인 필요 | 확인 필요 |

**가장 안전한 선택: 모의고사 답안을 `data.history`에 넣지 않는다.** `data.mockExam.answers`와
Firestore 문서에만 남긴다. 그러면 위 네 줄 중 세 줄이 손댈 필요 없이 해결된다.
대신 "오늘 푼 문제"에 모의고사가 안 잡히는데, 그건 결과 페이지가 따로 보여주므로 문제되지 않는다.

## 7. 결과 페이지

**점수는 정답률(%)로만 낸다.** 자작문제에는 공식 배점이 없다. 한능검 기출 회차처럼 100점 만점
환산을 하면 3급 기준(60점)과 혼동된다 — 그건 `Hanneung.stats`가 기출에만 쓰는 값이다.

- **점수**: `correct/total` 과 % (예: `37/50 · 74%`)
- **걸린 시간**: 총 소요 + 문항 평균. `startedAt`~`finishedAt`.
- **취약 파트**: 강의별·주제별 정답률 표. 문항 수가 적은 파트는 표본이 작다고 같이 표기할 것
  (3문항 중 1개 틀린 걸 "33% 취약"으로 보여주면 오독한다).
- **오답 목록**: 문항 + 내 답 + 정답 + 해설. 여기서 처음으로 해설을 본다.
- **지난 회차**: 같은 범위의 이전 결과와 추이.

## 8. 테스트 계획

기존 `drill-app.test.cjs`가 모드별 출제를 검증하는 방식을 그대로 따른다.

1. 시작 → 50문항(또는 범위 전량)이 확정되고, 같은 범위를 다시 열어도 **같은 시험지**가 나온다.
2. 진행 중에는 시작 버튼이 없고, 새로고침(상태 재적재) 후에도 **이어서** 풀린다.
3. 푸는 동안 **채점·해설이 뜨지 않는다**(`quizFeedback`이 생기지 않는다).
4. 마지막 문항을 풀면 결과가 나오고 시작 버튼이 **다시 생긴다**.
5. 시험 전후로 `card.due`·`interval`·`ease`·`retryAt`가 **하나도 바뀌지 않는다**.
6. 시험 직후 평소 모드의 "풀어야 할 문제 N/M"이 **시험 전과 같다**.
7. 07강처럼 50 미만인 범위는 전량이 나오고 "40문항"으로 표기된다.

## 9. 결정이 필요한 것

1. **범위 단위**: 강의만? 주제·요약자료·전체도? (07강 40문항 문제는 묶음 범위를 허용하면 해소)
2. **제한 시간**: 한능검은 80분/50문항. 타이머를 걸 것인가, 재기만 할 것인가.
3. **중간 이탈**: 시험 중 나가면 (a) 진행 저장 후 재개 (b) 무효 처리. 계획서는 (a) 가정.
4. **같은 문제 재출제**: 지난 시험에 나온 문항을 다음 시험에서 뺄 것인가.

## 10. 보류 이유와 재개 조건

2026-09-12에 한 번 보류했던 이유(자작문제가 전부 선사~남북국이라 "전범위"가 안 됨)는
**범위별 모의고사라 해소됐다.** 지금 자작문제는 조선 전기까지 와 있다.

남은 보류 이유는 하나다 — **즉시 채점을 끄는 흐름이 앱에서 가장 큰 구조 변경**이고,
진도(강의 늘리기)가 우선이기 때문이다. 재개할 때 이 문서의 3·4·6절부터 읽으면 된다.
특히 **6절(통계 오염)**이 이 기능에서 제일 조용하고 제일 아픈 함정이다.
